# Codebase Audit - 2026-07-28

This audit checks all disciplines in the sizing code. The disciplines are Geometry, Aerodynamics,
Propulsion, Weights, Mission, Tail Sizing, and Constraint Analysis. The audit also checks the sizing-loop
code and the dependency-injection (DI) structure.

The team did this audit after commit `68f13c3` and commit `7e5c195`. These commits added
`SizingLoopL1`, `SizingLoopL2`, `ControlSurfaceSizer`, and the full tail-sizing discipline.

This audit is read-only. The team did not change any code during this audit. This report lists findings
for review. The team has not fixed any finding yet.

## Method

The audit method has two steps.

Step one: run the baseline test suite, `run_all_tests`.

Step two: run seven review passes at the same time. Four passes use an equation expert. Each equation
expert checks one discipline: Geometry, Aerodynamics, Propulsion, or Weights. Each expert checks the
equations, the citations, and the test values for that discipline. One pass uses a general-purpose
agent. This agent checks Mission, Tail Sizing, and Constraint Analysis. No dedicated equation expert
exists for these three disciplines. One pass uses the `matlab-oop-expert` agent. This agent checks the
structure of each Tier-3 constructor. This agent confirms that each dependency injection is real. A real
dependency injection reads live data from another object. It does not copy the data one time and then
keep an old copy. This agent also confirms correct use of `Dependent` properties.

## Severity levels

This report uses three severity levels.

**HIGH**: a real defect in an equation or in logic. Or, a citation that points to the wrong source.

**MEDIUM**: a gap in a citation, an untested code path, or a break from a project convention. The
impact is possible, but the team has not confirmed it yet.

**LOW**: a cosmetic issue or a documentation-only issue.

This report does not list a finding if a subplan's own TODO list already tracks it. For example,
section 8 of `05_weights.md` already tracks some findings. This report lists only new findings.

### CC-1. FIXED: wrong Raymer edition in citations. Weights and Propulsion disagree.

The Weights discipline cites "Raymer 7th ed." 32 times. These citations are in `WeightsL1.m`,
`WeightsL2.m`, `WeightsL3.m`, `WeightsModelL1.m`, `WeightsModelL2.m`, `WeightsModelL3.m`, all six
related `.md` files, and `docs/subplans/05_weights.md`.

This repo has one source file for these equations:
`temp_AI/docs/disciplines/reference_extracts/raymer_data.md`, lines 1-3. This source file names the
6th edition. This repo has no 7th-edition source file anywhere.

This citation does not agree with the Propulsion discipline. `PropL2.m`, line 8, cites Eq. 10.10,
the engine dry weight equation, as "Raymer 6th ed. Sec. 10.3.2." The Weights code uses this same
equation. `F16WeightsL2.m`, line 266, and `F16WeightsL3.m`, line 528, both call
`PropL2.engine_weight_AB` to get this value. So one file cites the equation as 6th edition. Another
file cites the same equation as 7th edition.

Every other discipline cites "6th ed." This list includes `GeomL2.m`, `AeroL2.m`,
`StallConstraint.m`, and `TakeoffConstraint.m`. Only Weights uses "7th ed."

Section 9, item 1, of `docs/subplans/05_weights.md` records a related change. This record shows a
fix to a table number, from Table 6.1 to Table 3.1. The record does not give a reason for the edition
change. The record does not show a user decision about the edition change. Compare this to the
tail-sizing decision about Table 6.4. That decision has a clear date in `VnV/BrandtF16A/todo.md`,
lines 209-212.

This error does not change any number in the equation. Both source extracts show the same numbers.
But the citation sends a reader to the wrong physical book, or the wrong PDF file.

**Resolution (2026-07-30):** Casey read the actual physical Raymer 6th edition PDF directly, pages
572-574, and confirmed Eq. 15.1 through Eq. 15.24 appear there verbatim, matching this code's
equation numbers exactly. Table 3.1 and Table 15.2 are confirmed 6th edition too. Every one of the
32 code citations and 13 subplan citations that wrongly said "7th ed." is now corrected to "6th ed."
One equation stays a real, confirmed exception: Eq. 10.10, the dry engine weight, is genuinely 7th
edition, per Sarojini (who has that edition) — both the Weights and Propulsion citations for this one
equation now correctly read "7th ed.", and this is the only equation where the two disciplines
intentionally still differ from "6th ed." for a good reason, not by accident.

### CC-3. MEDIUM to HIGH: `F16TailL1` and `F16TailL2` freeze derived values in non-`Dependent`
properties.

Two separate review passes found this same issue on their own. This gives the finding strong
support. In `F16TailL1.m`, lines 42-53, the properties `c_HT` and `c_VT` are
`properties (SetAccess = private)`. The constructor computes each value one time, through the call
`TailL1.compute_tail_volume_coeffs('jet_fighter', true, true)`. Neither property is a
`properties (Dependent)` value with a live getter method. Every other Tier-3 class in this repo uses
a live getter for a derived value. `F16GeomL2.m` shows the correct pattern. CLAUDE.md's
"Optimization-ready property design" section states this rule directly.

This problem is worse than a normal stale-value risk. The real driver values, `aircraft_category`,
`has_rss`, and `has_all_moving_tail`, are not object properties at all. Each value is a literal word
written directly into the one no-argument constructor call. So no caller, and no optimizer, can
change these values on an existing object today.

`F16TailL2.m`, lines 47-50 and 58-69, has the same structural pattern. The properties `C_HT` and
`C_VT` are also frozen as `SetAccess = private`. But these two values are true hardcoded spec
constants. The source is the F-16 row of Nicolai and Carichner's Table 11.6. This case is similar to
`F16GeomL2`'s own spec input, `tc_r_ht = 0.060`.

So the correct fix here is different. The team recommends plain, mutable `properties`, not
`Dependent` properties. There is no live computation to add here. The only problem is the
`SetAccess = private` lock. This lock does not match how every other Tier-3 class treats its own spec
constants.

Neither `TestTailL1.m` nor `TestTailL2.m` has a test for this convention. No test checks a live
mutation, and no test checks a read-only lock, for these four properties. Every other discipline has
this kind of test. So this gap in the code is also a gap in the test suite. The citations for these
values are correct: Raymer Table 6.4 for L1, and Nicolai Table 11.6 for L2.

### CC-4. LOW: a doc table transposes K1 and K2.

Two separate review passes found this same issue on their own. The file
`docs/subplans/06_constraint_analysis.md` prints the Master Equation in a table, near line 112. This
printed table swaps the K1 term and the K2 term. The actual code is correct. In `ThrustConstraint.m`,
the function `compute_B` uses K1 for the term that is linear in `(W/S)`. The function `compute_C`
uses K2 for the constant term. This matches the K-convention used everywhere else in the repo,
for example in `AerodynamicsBase.compute_CD`. Only the printed table in the subplan document is
wrong. This is a documentation-only fix.

`SizingLoopL1.m` and `SizingLoopL2.m` both switch to a new closure formula for the takeoff gross
weight, `W_TO`. The new formula is
`W_TO_new = W_payload / (1 - We/W_TO - W_fuel/W_TO)`. This is Raymer's takeoff-weight buildup

comments are clear and complete. The comments openly state that the equation number, "Eq. 3.4," comes
from the user, not from an independent check against a source in this repo.

formula's answer, 41,437.5 pounds-force versus 41,433.1 pounds-force, a gap of only 0.01%. So the team
confirmed that both formulas solve the same underlying equation, before the team switched to the new
formula. The new formula also converges in far fewer steps, 8 steps instead of 81 steps. The
iteration loop has a clear stopping tolerance, a maximum step count, and an under-relaxation factor.
So the loop cannot run forever, and the loop cannot silently accept a wrong answer.

`SizingLoopL2` requires both `W_TO` and `T_SL` to reach the stopping tolerance, which matches the
plan in subplan 08. For dependency injection: every change, for example `obj.geom.S_ref = ...`,

already-injected `handle`-class objects. This matches the pattern that the first audit already
confirmed as correct for these two files. No value gets copied into a separate, private copy.

The tests in `TestF16SizingStudies` did not change in this diff, and all of these tests still pass
with the new formula, as the fresh baseline run above shows. This gives direct proof that the new
formula still gives a sound, converged value for `W_TO`.
