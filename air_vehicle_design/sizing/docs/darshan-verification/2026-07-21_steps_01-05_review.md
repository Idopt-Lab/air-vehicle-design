## Bottom line

Casey's work should not be trusted as-is. The equations that exist are mostly textbook-correct, but a recurring pattern hides the bugs: **tests that recompute the same formula as the code being tested** (so they can't fail), **derived quantities frozen as hardcoded constants** instead of computed, and **tolerance bands wide enough to swallow the very errors present**. Concretely, `TestWeightsL3.m` **fails 3 of 17 tests right now** when actually run — reproduced independently — which directly violates the subplan's own gate ("all tests must pass before Step 6 begins").

## Cross-cutting patterns (the meta-problem)

1. **Self-referential tests** — a test computes "expected" by duplicating a citation-specific empirical coefficient that is also hardcoded in the source (e.g. several `TestWeightsL2`/`L3` "formula" tests copying a Raymer Table 15.2 unit weight). A shared transcription error from the textbook is invisible to these. (32 such tests plus 3 related "fidelity-parity" tests were found and removed on 2026-07-21 — see addendum above.)
2. **Hand-derived-once, then frozen as a constant** — geometry's wing sweep, MAC, chord, and AR are never computed in code; they're hardcoded numbers with a comment showing the formula. Nothing enforces they're actually consistent, and one (wing sweep) isn't.
3. **Tolerances that appear tuned to the known error, not derived independently** — ±30% absolute in propulsion, ±20–40% in weights, consistently landing just wide enough to pass the current (buggy) output.
4. **Self-flagged, unresolved uncertainty shipped anyway** — multiple `TODO`/`[verify]` comments admitting an equation or constant might be wrong, with zero test coverage on that function.

## Geometry (L1/L2/L3)

- **`examples/F16A/F16GeomL2.m:30`** (and `F16GeomL3.m:42`) — `QC_sweep_wing = 37` deg, commented "derived from planform," but the correct value from the standard sweep-conversion identity using the model's own AR=3.0/λ=0.2275/LE sweep=40° is **≈32.2°**. Applying the same formula to the HT gives 36.8°≈37° — strongly suggesting the HT's sweep was copy-pasted onto the wing. This feeds directly into `AeroL2`/`AeroL3`'s `CL_alpha` and `CLmax`, shifting them by −3% to −5.6%.
- **Root cause of the above**: `GeomL2`/`GeomL3` never actually compute `c_root`, `c_tip`, `b`, `AR`, or MAC (`cbar`) anywhere — despite the spec (`02_geometry.md:68-69`) requiring these formulas. Every F16 example just hardcodes the numbers as comments. Independently computing MAC from the stated geometry gives 11.32 ft — a value that appears nowhere in the codebase.
- **Zero test coverage for any of it**: no test anywhere checks `b`, `AR`, `c_root`, `c_tip`, `cbar`, or sweep — directly contradicting the spec's own required tests (`02_geometry.md:99,101,107-108`). This is exactly why the sweep bug above shipped with a fully green suite (17/17, 23/23).
- **`examples/F16A/F16GeomL1.m:19,42-44`** — docstring claims `get_L_fus` populates `obj.L_fuselage`; it doesn't (it only returns a value). Property stays 0 forever. Currently harmless (nothing reads the property directly) but the abstract contract requires it.
- **`GeomL2.m:53-60` / `GeomL3.m:67-74`** (duplicated verbatim) — Roskam fuselage wetted-area formula is only valid for fineness ratio > 2; unguarded, and a plausible short/wide fuselage input returns a **complex number** with no error.
- **`GeomL3.m:58-65`** (`compute_roskam_planform`) — unguarded division by `(1+λ)` and `(tc_r/tc_t)`; a zero tip t/c silently returns `Inf`.
- Coding practice: no property validation anywhere in the concrete F16 geometry classes (`S_ref`, `lambda_wing`, `tc_wing` all accept nonsensical values silently).

## Aerodynamics (L1/L2/L3)

- **`src/disciplines/aerodynamics/AeroL2.m:36-56`** — `drag_polar`, `get_CD0`, `get_e_osw`, `get_K1` all delegate verbatim to `AeroL1` (confirmed by reading the file directly). L2 never implements the Reynolds-number-based `Cf` method the spec assigns it — L1 and L2 produce bit-for-bit identical drag polars, and `TestAeroL2` asserts this identity as a *required pass condition*, locking in the missing feature.
- **`AeroL1.m:50-54,136-145`** — at exactly M=1.0, `drag_polar` routes to `K1_supersonic`, which explicitly throws an error for M≤1 → **guaranteed crash at Mach 1.0**. Worse, hand-rederiving the algebra: for 1.0<M<1.0138, the denominator `4·AR·β−2` goes negative before the numerator does, making `K1` (and thus induced drag) **negative** — lift reducing drag, which is unphysical. No test samples this band; Brandt's reference table jumps straight over it.
- **`F16AeroL1/L2/L3.m`** — `CL_minD` is hardcoded to `0.0` in all three classes despite each declaring `alpha_L0=-1.01°` (a cambered NACA 64A204 airfoil) specifically to feed it. The method that would compute it is simply never called, so the polar's offset term (K2) is always 0 when it should be roughly −0.007 to −0.013.
- **`AeroL3.m:248-260`** (`FF_body`) — invents an unsourced piecewise split (fineness ratio ≤6 vs >6) not in the spec, which specifies one universal formula (`03_aerodynamics.md:109`). For the F-16 duct this underestimates form factor by 8.8%. `TestAeroL3` computes its "expected" value with the same fabricated split, so it can't catch this.
- **`tests/disciplines/TestAeroL2.m:42-69`** — `testCLalphaAtMachZero` and `testCLalphaAtMach06` both assert against the *same* hardcoded 3.1121 with a ±0.20 absolute tolerance, even though the actual values at M=0 and M=0.6 genuinely differ (3.01 vs 3.22) — the tests can't validate the Mach dependence they're named for.
- **`examples/F16A/F16AeroL3.m:167-171`** (`get_CLmax`) — literal `TODO` stub that ignores all L3 data and just calls L1's category lookup; `TestAeroL3` then asserts L1 must equal L3 exactly, enshrining the gap as a passing test.
- Demonstrated tolerance weakness: swapping the correct swept-wing Oswald-efficiency formula for the wrong straight-wing one at the F-16's own AR/sweep only shifts `e` by 6.9% — comfortably inside the ±20% band most tests use, so a real formula-selection bug of this kind would go undetected.

## Propulsion (L1/L2)

- **`src/disciplines/propulsion/PropL1.m:89-105`** — `lookup_TSFC_table`: the `turboprop` row (cruise=0.90, loiter=0.80) is byte-for-byte identical to `turbojet`, while the other three rows are all mutually distinct and turbofan rows carry an explicit justifying comment. ## Recommendation

Don't accept this as a passing "Step 5 complete." At minimum:

1. Fix the failing weights tests before anything downstream builds on them.
2. Replace the self-referential/tautological tests with independently-derived expected values.
3. Tighten every tolerance that was evidently reverse-engineered from the current output.
4. Make geometry actually *compute* planform quantities (b, AR, c_root, c_tip, MAC, sweep conversions) instead of hand-freezing them as constants — this is how the wing-sweep bug shipped invisibly.
