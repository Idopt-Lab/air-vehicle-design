# b777_L1 — companion doc

Companion to `examples/B777/inputs/b777_L1.json` (not yet written) — the Boeing 777-200LR
Level-1 **SPEC** data (what the aircraft IS). Every discipline method for this example uses the
metabook Chapter 4 statistical method at "L1" discipline fidelity. Both the L1 and the L2 sizing
algorithms read this one spec file.

**SCOPE GUARD.** This file holds SPEC data only — reference areas, aspect ratio, taper, fuselage
size, engine thrust, engine model, config-polar table. It never holds REQUIREMENTS (what the
aircraft must DO — field lengths, climb gradients, cruise point, range: those stay in
`examples/B777/inputs/b777_requirements.json`). The `aircraft_category` sits at the top level, not
inside a discipline block.

**Provenance.** The metabook worked Example 4.2 is the ground-truth source; it is a SECONDARY
source that cites Raymer / Roskam / Mattingly. Citations below give the metabook Eq/Table and the
primary table the metabook itself names. `[metabook §4.11]` = the worked Example 4.2 text,
`docs/reference_extracts/metabook_data.md`.

**Discrepancy note.** The metabook wetted-area exponent (`d = 0.7531`) disagrees with the repo's
current `GeomL1.lookup_swet` transport_jet row (`d = 0.7351`). This is logged as discrepancy **D3**
in `metabook_data.md` "Known discrepancies", RESOLVED (Sarojini 2026-08-13) in favour of the
metabook value; the repo row is to be corrected in the src-extension batch. The B777 example uses
`d = 0.7531`.

### 2.1 `S_wet_rest` arithmetic (show the decomposition)

The metabook Eq. 4.58 splits total wetted area into a wing part (approximated as `2·S`) and the
rest of the aircraft:

```
Swet      = 10^0.0199 * 766,800^0.7531 = 28,291 ft²          (metabook Eq. 4.42)
Swet      = Swet_rest + 2*S              (metabook Eq. 4.58)
Swet_rest = 28,291 - 2*4,605 = 28,291 - 9,210 = 19,081 ft²
```

`S_wet_rest = 19,081 ft²` is the wetted area of everything except the wing. It is carried as a spec
input so the L2 sizing algorithm can recompute `CD0(S)` when it varies the wing area S (Eq. 4.58):
`CD0 = Cf * (S_wet_rest + 2*S) / S`. The full-airplane MTOW-regressed `Swet = 28,291 ft²` from
Eq. 4.42 is a DERIVED cross-check, not a stored input — it is regenerated from the Eq. 4.9
regression at the baseline W0.

**Citation caveat.** The `766,800` in Eq. 4.42 is the baseline MTOW (Table 4.3); the `S = 4605`
divisor is `S_ref` above. Both are cited. The exponent `0.7531` is the metabook value (D3), not the
current repo `0.7351`.

### 2.3 Wing taper — decision, not carried (recommendation)

The metabook Example 4.2 never uses the wing taper ratio. It builds the drag polars from `AR`, `e`,
and the config `ΔCD0` values only, and it takes `Swet` from the MTOW regression, not from planform
chords. So MAC is not needed for any L1 equation in this example.

- **Recommendation: do NOT carry `wing_taper` at L1.** Where a mean chord is genuinely needed (e.g.
  a future tail-volume path), use the standard mean chord `cbar = S/b` [metabook Eq. 11.5 note,
  `c_bar = S/b`], which needs only `S_ref` and `AR` (both already inputs: `b = sqrt(AR*S_ref)`).
- If a later fidelity step needs the true trapezoidal MAC, add `wing_taper` then with a cited
  777-200LR value (which is itself a `_TODO` — no taper appears in the metabook). Recording the
  choice here avoids carrying an uncited taper that no equation reads.

### 2.4 Tail sizing — new row needed later (flag)

The metabook Chapter 8 gives jet-transport tail volume coefficients `cVT ≈ 0.09`, `cHT ≈ 1.0`
[metabook Eqs. 8.1/8.2]. The repo `TailL1.lookup_tail_volume_coeffs` currently implements the
`jet_fighter` row ONLY and errors on any other category. A `jet_transport` row (`c_HT = 1.0`,
`c_VT = 0.09`) must be ADDED to `TailL1` in the implementation phase before the B777 can size a
tail through that toolbox. This is a code change, not a JSON input — flagged here so it is not
missed. No tail block is required in `b777_L1.json` for the Example 4.2 sizing itself (tail is not
exercised by Eqs. 4.42–4.57).

### 3.1 Config polars — TOOLBOX-DERIVED, no longer a JSON table

`B777AeroL1` builds every config polar from two shared read-only toolbox tables plus the live
geometry; nothing is read from a JSON `config_polars` block (it no longer exists). Derivation path:

```
Cfe        = AeroL2.lookup_Cfe(translate(aircraft_category))     [Raymer Table 12.3, civil_transport = 0.0026]
CD0_clean  = AeroL2.CD0_from_Cf(Cfe, S_wet, S_ref)               [metabook Eq. 4.8 = Raymer Eq. 12.23], tracks S live
e(cfg)     = UPPER bound of AeroL1.Delta_CD0.e_osw[cfg-row]      [Roskam Table 3.6]
ΔCD0(cfg)  = UPPER bound of AeroL1.Delta_CD0.Delta_CD0[cfg-row]  [Roskam Table 3.6]
CD0(cfg)   = CD0_clean + ΔCD0(cfg)                               [metabook §4.11 config increment]
K1(cfg)    = 1 / (pi * AR * e(cfg))                              [metabook Eq. 2.10 = Raymer Eq. 12.50], tracks AR live
K2         = 0                                                    (uncambered-basis metabook high-lift polar)
```

**Upper-bound note (the one design choice).** `AeroL1.Delta_CD0` (Roskam Table 3.6) gives each ΔCD0
and e_osw as a RANGE. `F16AeroL1` reads the MEAN of each range (its private `roskam_Delta_CD0` /
`roskam_e_osw` call `mean(row.…{1})`). The B777 follows the metabook Example 4.2 convention and reads
the UPPER bound of each range instead. This is the single modelling decision in D10; both aircraft
read the SAME `AeroL1.Delta_CD0` Constant — no toolbox edit.

`AeroL1.Delta_CD0` (Roskam Table 3.6) rows and the upper bound this block uses:

| row | ΔCD0 range | ΔCD0 upper | e_osw range | e_osw upper |
|---|---|---|---|---|
| `clean` | [0.000 0.000] | 0.000 | [0.80 0.85] | 0.85 |
| `takeoff_flaps` | [0.010 0.020] | 0.020 | [0.75 0.80] | 0.80 |
| `landing_flaps` | [0.055 0.075] | 0.075 | [0.70 0.75] | 0.75 |
| `landing_gear` | [0.015 0.025] | 0.025 | NaN | — |

**The 6→4 mapping (six B777 configs onto four Roskam rows).** The FAR-25 constraint set needs six
config strings; Roskam Table 3.6 gives four rows. Gear-down configs ADD the `landing_gear` ΔCD0
upper bound (0.025) onto the flap row; e follows the flap row (gear has no e_osw). Approach is the
metabook Climb-6 mean of the two gear-down rows.

| config string | Roskam row(s) → ΔCD0 | e used | CLmax basis |
|---|---|---|---|
| `clean` | clean → 0.000 | 0.85 (clean upper) | `CLmax_clean` |
| `takeoff_flaps_gear_up` | takeoff_flaps → 0.020 | 0.80 | `CLmax_takeoff` |
| `takeoff_flaps_gear_down` | takeoff_flaps + landing_gear → 0.020 + 0.025 = 0.045 | 0.80 | `CLmax_takeoff` |
| `landing_flaps_gear_up` | landing_flaps → 0.075 | 0.75 | `CLmax_landing` |
| `landing_flaps_gear_down` | landing_flaps + landing_gear → 0.075 + 0.025 = 0.100 | 0.75 | `CLmax_landing` |
| `approach` | mean(0.045, 0.100) = 0.0725 | 0.75 | 0.85 · `CLmax_landing` — §3.3 |

**As-built polars this derivation reproduces** (baseline S_ref = 4605, AR = 9.8; CD0_clean =
`0.0026·28291/4605` = 0.01597):

| config string | CD0 | K1 = 1/(π·AR·e) | CLmax |
|---|---|---|---|
| `clean` | 0.01597 | 0.03821 | 0.9 |
| `takeoff_flaps_gear_up` | 0.03597 | 0.04060 | 2.0 |
| `takeoff_flaps_gear_down` | 0.06097 | 0.04060 | 2.0 |
| `landing_flaps_gear_up` | 0.09097 | 0.04331 | 2.6 |
| `landing_flaps_gear_down` | 0.11597 | 0.04331 | 2.6 |
| `approach` | 0.08847 | 0.04331 | 2.21 |

The `CD0` column reproduces the previously-hardcoded `config_polars` CD0 EXACTLY. **The `K1` column
shifts in the 4th–5th decimal** because the derived e is the EXACT Table 3.6 upper bound
(0.85 / 0.80 / 0.75), whereas the removed `config_polars.K1` rows (0.03815 / 0.04054 / 0.04324) were
computed from the metabook's rounded-up "e implied" values (0.8515 / 0.8013 / 0.7513). See §3.5 — the
derived 0.03821 is the value the current `e_clean = 0.85` input ALREADY produces through `drag_polar`

input, so the refactor removes a pre-existing inconsistency rather than introducing one.

The six config strings match the set `AerodynamicsBase.get_config_polar` validates, exactly:

### 3.3 Approach polar (derived from the takeoff/landing gear-down rows)

The metabook approximates the balked-landing (Climb 6) approach configuration as the mean of the
takeoff and landing gear-down CD0, and approach CLmax as 0.85 of landing CLmax [metabook §4.11
Climb 6 note]. With the toolbox-derived gear-down ΔCD0 upper bounds:

```
ΔCD0_approach  = mean(0.045, 0.100) = 0.0725          (mean of the two gear-down ΔCD0 upper bounds)
CD0_approach   = 0.01597 + 0.0725   = 0.08847         (equivalently mean(0.06097, 0.11597))
CLmax_approach = 0.85 * CLmax_landing = 0.85 * 2.6 = 2.21
K1_approach    = 1/(π·9.8·0.75)     = 0.04331         (landing-flaps induced factor)
```

`CD0_approach = 0.08847` and `CLmax_approach = 2.21` are DERIVED, not independent inputs.
`B777AeroL1.get_config_polar("approach")` computes them so a change to the takeoff/landing rows or to
`CLmax_landing` propagates.

### 3.4 Cfe — toolbox lookup + the `jet_transport → civil_transport` translation

`Cfe` is no longer a JSON number. `B777AeroL1` reads it from `AeroL2.lookup_Cfe`, which carries the
Raymer Table 12.3 `civil_transport` row = **0.0026** — the exact value the JSON used to hardcode. The
canonical top-level `aircraft_category` is `jet_transport`, but the `AeroL2.lookup_Cfe` table prints
its row as `civil_transport`, so `B777AeroL1` translates the canonical value to that table's own row
name (`jet_transport → civil_transport`), mirroring `AeroL1.to_CLmax_table_row`'s
`jet_fighter → fighter` idiom. Do NOT rename the table row to match the key — the row name is what
Raymer Table 12.3 prints. `AeroL2.lookup_Cfe`'s own error message states the intent directly: "Add
the row with its cited table value rather than passing a number in through the input JSON."

decimal versus the removed `config_polars.K1` rows:

| config | e used (Table 3.6 upper) | K1 derived | K1 removed (JSON) | e back-implied by JSON K1 |
|---|---|---|---|---|
| clean | 0.85 | 0.03821 | 0.03815 | 0.8515 |

### 4.2 Thrust lapse — `m` is a gate decision (D5)

The metabook Example 4.2 uses `alpha = sigma^0.6` (Eqs. 4.55–4.57), the GENERIC Eq. 10.9 fit with
`m = 0.6`, with no engine-type justification. The metabook's OWN GE90 Table 10.1 data (the real 777
engine) fits `m ≈ 1.0–1.1` for a high-BPR turbofan. `PropL1.lookup_lapse_exponent` currently
returns `m = 0.6` for `high_bypass_turbofan`. Making `m` a cited JSON input (`lapse_exponent_m`)
lets the choice be explicit. Recommendation and the two options are in `B777_decisions.md` §1.

`PropL1.get_thrust_lapse` computes `alpha = sigma^m` with `sigma = rho/rho_SL` from the
`AircraftState` — so the B777 model uses ISA density from the state, not the metabook's printed
off-ISA density ratios (0.2846 at "40,000 ft", 0.2331 at "42,000 ft"). Those printed ratios are used
ONLY by the comparison report, for parity with the printed equations (see D5).

### 4.3 TSFC — Mattingly high-BPR

The metabook Eq. 10.11 high-BPR turbofan form:

```
c = (0.4 + 0.45*M) * sqrt(theta)     [1/hr]     (metabook Eq. 10.11 = Mattingly 1996 Eq. 1.36a)
```

`theta = T_altitude / T_SL` (temperature ratio, from `AircraftState`). This is a METHOD, not a
stored number. The categorical `PropL1.get_TSFC` (0.50 cruise / 0.40 loiter for
`high_bypass_turbofan`, [Raymer Table 3.3]) is the crude L1 fallback; the B777 mission analysis
should prefer the Mattingly Eq. 10.11 Mach/theta-dependent form. The GE90 SLS SFC range 0.29–0.31
[metabook Table 10.1] is a cross-check target, not an input.

### 5.2 Areal densities and engine-weight regression

The Raymer Table 15.2 transport/bomber densities (wing 10, H-tail 5.5, V-tail 5.5, fuselage 5.0
lb/ft²) and the fraction-based rows (landing gear 0.043·W0, all-else-empty 0.17·W0) are all in
`metabook_data.md` Ch. 7 (Raymer Table 15.2 and the fraction table). They are toolbox Constants
selected by `aircraft_category`, matching how the F-16A L2 weights class reads its own densities.

Engine weight uses the Roskam regression form [metabook Ch. 7, Eqs. 7.13–7.19]:

```
Weng_dry     = 0.521 * T0^0.9
Weng_oil     = 0.082 * T0^0.65
Weng_rev     = 0.034 * T0
Weng_control = 0.26  * T0^0.5
Weng_start   = 9.33  * (Weng_dry/1000)^1.078
Wengine      = sum of the above          (metabook Eq. 7.19)
```

`T0` = per-engine SLS thrust [lbf]. These coefficients are toolbox Constants [Roskam; metabook
Ch. 7], not JSON inputs. Cross-check target: the GE90 uninstalled weight 17,300 lb [metabook
Table 10.1].
