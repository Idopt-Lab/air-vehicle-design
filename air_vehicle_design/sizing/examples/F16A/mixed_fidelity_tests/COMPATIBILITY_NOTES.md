# Mixed-fidelity compatibility notes

This file summarizes the RECURRING structural patterns behind why most of
the 1536 combinations in `sweep_report.csv` do not construct or converge.
It is a "why" summary, not the authoritative list -- for the full
per-combination detail (which exact combos fail, at which stage, with what
message), always read `sweep_report.csv`, regenerated by
`run_fidelity_sweep()`.

1. **Aero at L2/L3 requires Geometry at L2/L3.** `F16AeroL2`/`F16AeroL3`
   guard their `geom` argument with
   `mustBeA(geom, ["GeometryModelL2", "GeometryModelL3"])`. Geometry=L1 or
   Geometry=Brandt paired with Aero=L2/L3 fails at construction (stage
   `"aero"`).

2. **Weights at L2/L3 requires Geometry at L2/L3.** Same guard shape as #1,
   added to `F16WeightsL2`/`F16WeightsL3` by this work (loosened from a
   single fixed tier to accept either L2 or L3 -- mirroring Aero's existing
   precedent). Geometry=L1 or Geometry=Brandt paired with Weights=L2/L3
   fails at construction (stage `"weights"`).

3. **Brandt Aero/Weights/Mission each build their own PRIVATE `BrandtGeometry`
   internally**, independent of whatever Geometry level the rest of a combo
   uses. `BrandtAeroAdapter`/`BrandtWeightsAdapter`/`BrandtMissionAdapter`'s
   constructors never take an external geometry object -- no seam exists for
   one. Their numbers always reflect Brandt's own airframe, regardless of
   Geometry=L1/L2/L3/Brandt elsewhere in the same combo. This is expected
   "weirdness," not a bug: it is exactly what "each adapter must be usable
   independent of the rest of the combo's chosen levels" requires.

4. **Brandt Mission ignores whatever `aero`/`prop` objects are passed to
   `compute_fuel`, entirely.** `BrandtMissionAdapter.compute_fuel` accepts
   the arguments (to satisfy `MissionAnalysisBase`'s shared signature) but never
   reads them -- fuel burn comes from `BrandtMission`'s own private
   aero/engine/geometry triplet, built once in the adapter's constructor.
   Fuel burn at Mission=Brandt therefore never responds to a simultaneously
   chosen Aero/Propulsion level. A one-time `warning(...)` fires the first
   time `compute_fuel` is called on a given adapter instance.

5. **`BrandtEngine`/`BrandtGeometry` always load their own hardcoded
   `VnV/BrandtF16A/GroundTruth/f16a_geometry.json`**, ignoring whichever
   `f16a_L{1,2,3}.json` spec file the rest of a combo points at. There is no
   constructor argument on `BrandtPropAdapter`/`BrandtGeomAdapter` (as used
   by `build_fidelity_combo`) that would let a combo's chosen spec file
   reach Brandt's engine/geometry math.

6. **Geometry=Brandt is incompatible with framework Aero in {L2, L3} or
   framework Weights in {L2, L3}.** `BrandtGeomAdapter` only satisfies bare
   `GeometryBase` (`S_ref`/`S_wet`/`get_S_ref`/`get_S_wet`) -- it declares
   none of the ~20 planform properties `GeometryModelL2`/`GeometryModelL3`
   require, so it fails the same `mustBeA` guards described in #1/#2. This
   is a genuinely new incompatible combination introduced by adding Brandt
   as a level, not a pre-existing one.

7. **Propulsion has no L3 tier** (pre-existing, unrelated to this work) --
   there is no `propLv = "L3"` option in `build_fidelity_combo`/
   `run_fidelity_sweep`; the rest of the codebase's convention (design
   studies, `F16ConstraintSet.buildDisciplines`) is that `F16PropL2` serves
   the L3 rung, and this harness follows the same convention -- L3 disciplines
   are always paired with Propulsion in {L1, L2, Brandt}, never a dedicated
   L3 propulsion object.

8. **Swapping only Geometry (keeping Aero/Weights at L1) has no visible
   effect on results**, since `F16AeroL1`/`F16WeightsL1` never take an
   injected geometry object at all -- their constructors read only a spec
   JSON path. This is expected, harmless "weirdness," not a bug: at
   Aero=L1/Weights=L1, the Geometry axis is fully decorative for those two
   disciplines' own outputs (though it still affects anything else in the
   combo that DOES read `geom`, e.g. Weights=L2/L3 with Aero=L1).

9. **Weights at L2/L3 requires Propulsion to expose `bypass_ratio`, which
   only `F16PropL2` provides.** `F16WeightsL2.get.W_en` /
   `F16WeightsL3.get.W_en` read `obj.prop.bypass_ratio` directly (Raymer
   Eq. 10.10's `exp(-0.81*BPR)` term) -- but `bypass_ratio` is NOT part of
   `PropulsionBase`'s abstract contract, only a plain property `F16PropL2`
   happens to declare. `F16WeightsL2`/`F16WeightsL3`'s `prop` argument is
   typed as bare `PropulsionBase`, so this passes construction cleanly
   regardless of which Propulsion level is chosen, and only fails at
   RUNTIME -- inside the sizing loop, the first time `wts.OEW(W_TO)` reads
   `W_installed_engine` -> `W_en` -> `obj.prop.bypass_ratio` on a
   `F16PropL1` or `BrandtPropAdapter` object, neither of which declares that
   property. This surfaces in `sweep_report.csv` as a `runtime_error` row
   (stage `"loop"`) for every combination pairing Weights in {L2, L3} with
   Propulsion in {L1, Brandt}. This is a PRE-EXISTING latent gap in
   `PropulsionBase`'s contract (Propulsion=L1 paired with Weights=L2/L3 was
   already possible, and already broken, before this work touched anything)
   -- discovered, not introduced, by this sweep; fixing it (e.g. promoting
   `bypass_ratio` to `PropulsionBase`'s abstract contract) is out of this
   work's scope and is left for a future propulsion-discipline pass.

10. **Weights=L3 genuinely requires Geometry=L3, not just Geometry in
    {L2, L3}, despite passing #2's `mustBeA` guard.** `F16WeightsL3`'s
    Dependent getters (`get.F_w`/`get.B_h`/`get.H_t`/`get.H_v`/`get.L_t`/
    `get.S_r`/`get.AR_vt`/`get.lambda_vt`, `F16WeightsL3.m` around lines
    469-524) read nine properties (`F_w`, `B_h`, `H_t`, `H_v`, `L_t`, `S_r`,
    `AR_exposed_vt`, `lambda_exposed_vt`) that `GeometryModelL3` declares but
    `GeometryModelL2` does not. So Weights=L3 + Geometry=L2 passes
    construction (item #2's loosened guard genuinely accepts either tier),
    then fails at RUNTIME the first time `OEW(W_TO)` touches one of these
    nine -- a "no public property" error, stage `"loop"` in
    `sweep_report.csv`, not stage `"weights"`. `tests/disciplines/
    TestWeightsL3.m`'s `testWrongGeomTierErrorsAtConstruction` was updated to
    assert exactly this split (L1 rejected at construction; L2 accepted at
    construction, then errors on first `OEW` call). Unlike item #9, this one
    IS newly introduced by item #2's loosening -- the old exact-tier guard
    made it unreachable.

11. **`BrandtAeroAdapter` needed four extra methods beyond `AerodynamicsBase`'s
    formal two-method contract.** `F16ConstraintSet.build`'s
    `TakeoffConstraint`/`LandingConstraint` duck-type on `get_CLmax_TO()`/
    `get_CLmax_L()`/`get_Delta_CD0_TO()`/`get_Delta_CD0_L()` -- every
    `F16AeroL1/L2/L3` implements these, but they are not declared on
    `AerodynamicsBase`, so nothing caught their absence until Weights=Brandt/
    Aero=Brandt actually reached the constraints stage at runtime. Added:
    `get_CLmax_TO`/`get_CLmax_L` return Brandt's own `CLmax_takeoff`/
    `CLmax_landing` directly; `get_Delta_CD0_TO`/`get_Delta_CD0_L` both
    return `CD0_takeoff - CD0` since Brandt has only one flapped-config CD0
    (Miss!CD0_TO), no separate landing value -- a documented approximation,
    not a citation. All four are zero-arg, matching `F16AeroL2`'s own
    signatures (`TakeoffConstraint`/`LandingConstraint` dispatch on arity via
    metaclass reflection, so this must match one of the two arities every
    other `F16AeroL*` class uses).

13. **Loop=L2 requires Geometry in {L2, L3}** -- found by running the full
    sweep, not by code inspection. `SizingLoopL2.run` (`src/sizing/
    SizingLoopL2.m:170`) unconditionally calls `obj.geom.size_tail()`
    zero-arg, per `GeometryModelL2`/`GeometryModelL3`'s abstract contract
    (tail sizing absorbed into Geometry, 2026-08-03). This sweep run
    originally surfaced an `F16GeomL1` method of the same name but a
    different four-argument signature, which this codebase's own convention
    says should never have existed: L1 was never supposed to have tail
    sizing at all (Casey, 2026-08-05) -- "tail sizing is for L2 and up." That
    instance-level capability (the `GeometryModelL1` abstract declaration,
    `F16GeomL1`'s `size_tail` method, and its `c_HT`/`c_VT` properties) has
    since been removed entirely; L1 now has no `size_tail` in any shape.
    (`GeomL1.m`'s STATIC toolbox methods `size_tail`/`compute_tail_arm`/
    `compute_S_HT`/`compute_S_VT`/`compute_tail_volume_coeffs` are unaffected
    and unchanged -- those are shared low-level infrastructure `F16GeomL2`/
    `GeomL3.m` call directly, despite the file's name.) So `F16GeomL1` now
    fails the same way `BrandtGeomAdapter` always did -- "no such method" --
    rather than "Not enough input arguments." Net effect, unchanged: **every
    Loop=L2 combination with Geometry in {L1, Brandt} fails at the loop
    stage**, regardless of what any other discipline is set to -- a
    pre-existing gap in `SizingLoopL2` (it assumes any injected geometry
    object supports self-contained tail sizing), not something this work
    introduced or fixes; `SizingLoopL2` was previously only ever exercised
    with L2/L3 geometry (`design_study_02_L2.m`/`design_study_03_L3.m`), so
    this code path was simply never run before the sweep tried it.

14. **Mission in {L2, L3} requires Aero in {L2, L3}** -- also found by
    running the sweep. `src/disciplines/mission/MissionL2.m`/`MissionL3.m`
    (the static toolboxes `F16MissionL2`/`F16MissionL3.compute_fuel`
    delegate to) read `aero_obj.S_ref` directly, e.g. `MissionL2.m:210`:
    `aero_obj.compute_CL(W_in, state.q, aero_obj.S_ref)`. `S_ref` is NOT
    part of `AerodynamicsBase`'s two-method abstract contract -- it is a
    Dependent property `F16AeroL2`/`F16AeroL3` happen to declare (backed by
    their injected geometry object), but `F16AeroL1` has no injected
    geometry and declares no `S_ref` at all, and `BrandtAeroAdapter`
    likewise has no `S_ref` (only `drag_polar`/`get_CLmax`/the four takeoff-
    landing extras from item #11). So **Mission=L2/L3 paired with
    Aero in {L1, Brandt} fails at runtime** the first time `compute_fuel`
    reads `aero.S_ref` -- a stage `"loop"` `runtime_error` in
    `sweep_report.csv` (mission's `compute_fuel` is called from inside the
    sizing loop, not at mission construction, so this cannot be caught
    earlier). Pre-existing gap in `MissionL2`/`MissionL3`, not introduced by
    this work -- exposed because no design study before this sweep ever
    paired Mission=L2/L3 with Aero=L1.

    **UPDATE (2026-08-09): NO LONGER APPLIES.** The old `src/disciplines/
    mission/` was replaced by the aircraft-agnostic `src/core/mission/`
    (`MissionAnalysisL1`/`L2`). The new mission is dependency-injected with a
    GEOMETRY object and reads `geom.get_S_ref()` directly (never `aero.S_ref`),
    so mission fidelity no longer constrains aero fidelity -- `build_fidelity_combo`
    now builds every Mission=L1/L2/L3 via `MissionAnalysisL{1,2}.from_requirements(aero, prop, geom, ...)`.

15. **Two defects found and fixed during verification, not left as
    documented limitations:**
    - `BrandtWeightsAdapter.W_payload_fixed`/`.W_payload_expendable` were
      originally left `NaN` (reasoning that "no `WeightsL{1,2,3}` static
      reads them" -- true, but `SizingLoopL1.run`/`SizingLoopL2.run`
      themselves read `obj.wts.W_payload_fixed + obj.wts.W_payload_expendable`
      directly every iteration, so `NaN` poisoned `W_TO` on iteration 1 and
      every Weights=Brandt combo failed to converge). Fixed by reading
      `obj.brandt.inp.weight.perm_payload_lb`/`.exp_payload_lb` (700/4400
      lbf, Wt!B4/B5, Main!O16/O17 -- the same real spec values
      `F16WeightsL1/L2/L3` read from `f16a_L{1,2,3}.json`) in the
      constructor, since `BrandtWeight` already loads exactly these figures
      internally for its own `W_armament`/`W_fuel` terms.
    - `tests/run_all_tests.m` never added `VnV/` to the MATLAB path, so any
      test constructing a Brandt adapter failed with "Unrecognized function
      or variable 'BrandtGeometry'" (etc.) even though the adapter code
      itself was correct. Fixed by adding
      `addpath(genpath(fullfile(root, '..', 'VnV')))`.

For the T_SL/S_ref mutability decisions behind `BrandtPropAdapter`/
`BrandtGeomAdapter` (why their `T_SL`/`S_ref` are plain mutable properties
rather than read-only `Dependent`, and why mutating them does not feed back
into Brandt's own fixed engine/geometry math), see those two classes' own
header comments in `adapters/`.
